# Attendance Bot — документация проекта

Актуально на 17 сентября 2026 года.

## 1. Назначение и текущее состояние

Attendance Bot ведёт журнал посещаемости учебной группы через Telegram и VK.
Оба клиента используют одну бизнес-логику и одну базу. Google Sheets остаётся
редактируемым журналом: бот доставляет туда изменения, а worker периодически
забирает обратно намеренные ручные правки.

В текущем MVP реализованы:

- регистрация студента в Telegram и VK;
- одновременная привязка одного студента к обеим платформам;
- роли студента и старосты;
- выбор недели, даты, занятия и отметки;
- просмотр, изменение и удаление собственных отметок;
- заявки на `Б` и `У`, обязательная причина для `У`;
- уведомление старост текущей платформы о новой заявке;
- подтверждение и отклонение заявок старостой;
- недельный лимит `Б` с понедельника по воскресенье;
- единое меню привязок с карточкой студента и отвязкой одной или всех платформ;
- импорт структуры и двусторонняя синхронизация Google Sheets;
- аудит изменений, структурированные логи и резервные копии SQLite.

## 2. Архитектура

Зависимости направлены внутрь:

```text
presentation (Telegram / VK / CLI)
                │
                ▼
application (commands, queries, interactors)
                │
                ▼
domain (entities, value objects, policies)
                ▲
                │
port ◄──────── adapter (database, Google Sheets, notifications)
                ▲
                │
           di (composition root)
```

- `src/domain` содержит правила, не зависящие от фреймворков и внешних API.
- `src/application/command` изменяет состояние.
- `src/application/query` читает данные и возвращает DTO/view-модели.
- `src/application/base_interactor.py` задаёт границу вызова use case.
- `src/port` объявляет интерфейсы репозиториев и внешних сервисов.
- `src/adapter` реализует эти интерфейсы через SQLAlchemy и Google API.
- `src/presentation/telegram` и `src/presentation/vk` преобразуют события клиента
  в команды и запросы application-слоя.
- `src/di/providers` собирает отдельные контейнеры Telegram, VK и инфраструктуры.

Presentation не обращается к ORM или Google Sheets напрямую. Платформенные
идентификаторы преобразуются в универсальную пару
`IdentityProvider + external_user_id` на границе клиента.

## 3. Основные сценарии

### Регистрация

Пользователь выбирает себя из свободного для конкретной платформы списка.
Создаётся активная запись `external_accounts`. Один студент может иметь одну
активную запись Telegram и одну VK. Повторное использование одного внешнего
аккаунта другим студентом запрещено.

Староста видит единую карточку студента со всеми активными платформами. Можно
отвязать конкретный аккаунт либо все аккаунты студента после подтверждения.
Отвязка не удаляет студента, посещаемость или аудит.

Роль старосты хранится на студенте, поэтому действует во всех его привязанных
клиентах. `BOOTSTRAP_OWNER_TELEGRAM_IDS` и `BOOTSTRAP_OWNER_VK_IDS` используются для начального
назначения роли по числовому ID платформы; username для авторизации не подходит.

### Посещаемость

Занятия фильтруются по подгруппе и показываются постранично по неделям. Время
не ограничивает возможность поставить отметку. Доступны статусы:

| Внутренний статус | Интерфейс | Google Sheets |
|---|---:|---:|
| `present` | `+` | `✓` |
| `absent` | `Н` | `Н` |
| `bonus` | `Б` | `Б` |
| `excused` | `У` | `У` |

`sequence_number` — только устойчивый порядок строк внутри даты, не номер пары.
Пустая строка занятия, включая серую пустую строку, не импортируется и в боте
не показывается.

Создание, изменение и soft-delete отметки выполняются транзакционно вместе с
записью истории и постановкой задания синхронизации. Студент может исправить
или удалить только собственную отметку.

### Заявки `Б` и `У`

`Б` и `У` создаются как долгоживущие заявки на конкретное занятие. Для `У`
причина обязательна. Новая заявка отправляет уведомления старостам той
платформы, из которой она создана, после чего доступна в общем списке заявок.

При одобрении `Б` проверяется лимит `BONUS_WEEKLY_LIMIT`. Неделя считается с
понедельника по воскресенье в `DEFAULT_TIMEZONE`. Лимит рассчитывается по
актуальным неудалённым отметкам, поэтому освобождается при замене или удалении
`Б`; новая неделя автоматически имеет отдельный баланс. `У` лимит `Б` не
расходует.

### Google Sheets

`import_sheet` читает студентов с листа настроек и занятия с листа журнала,
обновляя `students`, `lessons` и `sheet_mappings`. Импорт идемпотентен;
исчезнувшие элементы деактивируются без удаления истории.

Изменение через бот создаёт или обновляет одну запись `sheet_sync_queue` на
отметку. Worker записывает только целевую ячейку и использует версию отметки,
повторные попытки и exponential backoff.

После отправки очереди worker периодически перечитывает журнал. Явные значения
`✓/+`, `Н`, `Б`, `У` считаются намеренной правкой таблицы и обновляют БД с
аудитом. Пустая ячейка удаляет существующую отметку. Если для отметки уже есть
ожидающая исходящая задача, обратная сверка пропускает её, чтобы не затереть
новое изменение бота старым значением таблицы.

Таким образом, таблица является внешним редактируемым источником состояния, но
надёжная доставка, аудит и прикладные ограничения обслуживаются БД.

## 4. Данные

| Таблица | Назначение |
|---|---|
| `students` | ФИО, подгруппа и активность студента |
| `external_accounts` | Активные и отвязанные аккаунты Telegram/VK |
| `student_roles` | Роли студента, включая старосту |
| `lessons` | Дата, технический порядок, предмет, подгруппа |
| `attendance` | Текущее состояние отметки и optimistic version |
| `attendance_history` | Неизменяемый аудит операций |
| `attendance_requests` | Заявки `Б` и `У`, причина и решение |
| `sheet_mappings` | Координаты и fingerprint объектов таблицы |
| `sheet_sync_queue` | Дедуплицированная очередь исходящих изменений |
| `processed_updates` | Подготовленное хранилище ID внешних событий |

`processed_updates` присутствует в схеме, но пока не подключено к обработчикам;
гарантия дедупликации повторной доставки Telegram/VK update ещё не завершена.

SQLite работает с foreign keys, WAL и `busy_timeout`. Для текущего объёма одной
учебной группы этого достаточно; перед масштабированием на несколько групп
нужен нагрузочный тест и, вероятно, PostgreSQL.

## 5. Точки запуска

| Модуль | Назначение |
|---|---|
| `python -m telegram_main` | Telegram long polling |
| `python -m vk_main` | VK long polling |
| `python -m sync_worker` | Постоянная синхронизация Google Sheets |
| `python -m sync_worker --once` | Одна пачка и одна сверка |
| `python -m import_sheet` | Ручной импорт структуры |
| `python -m backup` | Один резервный снимок |
| `python -m backup --loop` | Периодические снимки |

Для локальных команд из корня нужен `PYTHONPATH=src`; Docker image уже задаёт
его.

## 6. Конфигурация

Секретные значения задаются только в `.env` или secret manager. Основные поля:

| Переменная | Назначение |
|---|---|
| `TELEGRAM_BOT_TOKEN` | Токен Telegram-бота |
| `VK_BOT_TOKEN` | Ключ сообщества VK с доступом к сообщениям |
| `VK_GROUP_ID` | Числовой ID сообщества VK |
| `VK_API_VERSION` | Версия VK API |
| `DATABASE_URL` | URL SQLAlchemy; в Compose переопределён на `/data/attendance.db` |
| `GOOGLE_SPREADSHEET_ID` | ID таблицы из URL |
| `GOOGLE_SHEET_NAME` | Лист журнала |
| `GOOGLE_SETTINGS_SHEET_NAME` | Лист со студентами |
| `GOOGLE_CREDENTIALS_FILE` | Путь к JSON service account |
| `DEFAULT_TIMEZONE` | Часовой пояс правил недели |
| `BONUS_WEEKLY_LIMIT` | Недельный лимит `Б` |
| `BOOTSTRAP_OWNER_TELEGRAM_IDS` | Telegram ID для первоначальной роли владельца |
| `BOOTSTRAP_OWNER_VK_IDS` | VK ID для первоначальной роли владельца |
| `ROLE_NOTIFICATION_*` | Интервалы, блокировка и retry уведомлений о ролях |
| `SHEET_RECONCILIATION_INTERVAL_SECONDS` | Период чтения ручных правок |
| `BACKUP_*` | Интервал, каталог и политика хранения снимков |
| `OBSERVABILITY_HASH_KEY` | Секретный ключ стабильной псевдонимизации platform ID |
| `LOG_LEVEL` | Уровень JSON-логов |

Полный шаблон находится в `.env.example`. Реальный `.env` и каталог `secrets`
не должны попадать в Git.

## 7. Запуск

### Docker Compose

```bash
cp .env.example .env
mkdir -p runtime backups secrets
docker compose up --build -d
docker compose ps
docker compose logs -f telegram-bot vk-bot worker notification-worker backup
```

Сервисы:

- `migrate` применяет Alembic и завершается;
- `telegram-bot` обрабатывает Telegram;
- `vk-bot` обрабатывает VK;
- `worker` синхронизирует Google Sheets;
- `notification-worker` доставляет изменения ролей в Telegram и VK;
- `backup` создаёт снимки SQLite.

Bootstrap ID при запуске сопоставляются со студентами и сохраняются как роль
`owner`. Поэтому владелец получает управление старостами на всех своих
привязанных платформах. Назначение/снятие роли и постановка
platform-уведомлений выполняются в одной транзакции. Таблица
`role_notification_queue` обеспечивает повторную доставку новой клавиатуры при
временной недоступности Telegram или VK. Обычный староста не может назначать
или снимать роли.

Обновление структуры таблицы:

```bash
docker compose run --rm telegram-bot python -m import_sheet
```

Остановка без удаления данных:

```bash
docker compose down
```

## 8. Миграции и тесты

Актуальная история начинается с единой ревизии `ddb75d1bb7c0`; последующие
изменения применяются обычными миграциями Alembic. Старые development-ревизии
удалены. Существующую БД со старым
значением `alembic_version` необходимо сначала сохранить и пересоздать либо
вручную сверить со схемой перед сменой revision через `alembic stamp`.

```bash
poetry install
poetry run alembic upgrade head
poetry run alembic check
poetry run pytest
poetry run ruff check src tests
```

После изменения SQLAlchemy metadata:

```bash
poetry run alembic revision --autogenerate -m "описание"
```

Миграцию нужно прочитать вручную перед применением. Удалять локальную БД вместо
миграции допустимо только для одноразового тестового окружения.

## 9. Логи и диагностика

Процессы пишут структурированные JSON-логи через `structlog`. Каждое входящее
событие Telegram/VK получает `correlation_id`, `provider`, `operation`,
`external_update_id`, `duration_ms` и результат обработки. Контекст автоматически
доступен application-логам в рамках того же запроса.

Сырые platform ID заменяются стабильным HMAC-псевдонимом `external_user_ref`.
Username, ФИО, причины, комментарии, токены, credentials, пароли и секреты
централизованно заменяются на `[redacted]`. Для production необходимо задать
случайный `OBSERVABILITY_HASH_KEY`; его смена изменит псевдонимы в новых логах.
Compose использует ротацию Docker `json-file`: не более трёх файлов по 10 МБ
для каждого сервиса. Это ограничивает локальное хранение примерно 30 МБ на
контейнер, не считая небольших служебных файлов Docker.

```bash
docker compose logs -f telegram-bot
docker compose logs -f vk-bot
docker compose logs -f worker
docker compose logs -f backup
```

Недоступность Google API не должна останавливать ботов: задание остаётся в
очереди и повторяется worker. Состояние очереди пока просматривается через БД и
логи; отдельного административного экрана ещё нет.

Каждая итерация worker получает собственный `correlation_id`. Событие
`sheet_sync.batch.completed` содержит длительность пачки, количество заявленных
и завершённых задач, числа `pending/processing/failed` и возраст самой старой
задачи. `sheet_sync.reconciliation.completed` отдельно содержит длительность и
результаты обратной сверки таблицы. Ошибка итерации записывается как
`sheet_sync.iteration.failed` с типом ошибки и временем до повтора.

Каждый постоянный Compose-сервис имеет Docker healthcheck через
`python -m observability.healthcheck --service <name>`. Общая часть проверяет
соединение с БД и совпадение `alembic_version` с текущим head. Worker записывает heartbeat на
каждой итерации, включая итерации с ошибкой Google API; backup обновляет
heartbeat только после успешного снимка. Поэтому временная недоступность Google
не делает весь сервис unready, но зависший worker и давно не выполнявшийся
backup обнаруживаются.

```bash
docker compose ps
docker compose exec telegram-bot python -m observability.healthcheck --service telegram-bot
docker compose exec worker python -m observability.healthcheck --service worker
```

## 10. Резервное копирование и восстановление

`backup` использует SQLite Backup API, проверяет snapshot через
`PRAGMA integrity_check`, упаковывает его в gzip и выполняет ротацию: семь
последних снимков и по одному за четыре ISO-недели по умолчанию. Временные DB,
WAL, SHM и journal-файлы очищаются после операции.

В циклическом режиме рестарт контейнера не создаёт дублирующий архив: если
последний снимок моложе `BACKUP_INTERVAL_SECONDS`, процесс ждёт остаток
интервала. Ручной запуск без `--loop` всегда создаёт новый снимок.

Создание и проверка списка:

```bash
docker compose run --rm backup python -m backup
ls -lh backups
```

Восстановление проводится только после остановки всех процессов с доступом к
БД:

```bash
docker compose stop telegram-bot vk-bot worker backup
docker compose run --rm backup python -m backup \
  --restore /backups/attendance-YYYYMMDDTHHMMSSZ.sqlite3.gz --yes
docker compose up -d telegram-bot vk-bot worker backup
```

Перед заменой создаётся `pre-restore-*` архив текущей БД. Локальные архивы не
зашифрованы самим приложением: шифрование диска или внешнего backup storage —
обязанность окружения.

## 11. Безопасность и персональные данные

- JSON service account должен иметь доступ только к нужной непубличной таблице.
- Токены Telegram/VK и Google private key необходимо ротировать при утечке.
- Роль старосты проверяется внутри application handler, а не только меню клиента.
- Отвязка аккаунта не является удалением учебной истории.
- ФИО, platform ID, посещаемость и причины `У` являются персональными данными.
- До публичного запуска нужно заполнить владельца, контакты, основание и сроки
  хранения в `PRIVACY_POLICY.md` и контакт в `SECURITY.md`.

Подробнее: `SECURITY.md` и `PRIVACY_POLICY.md`.

## 12. Известные ограничения

- дедупликация повторно доставленных Telegram/VK updates не подключена;
- незавершённый ввод причины `У` в VK хранится в памяти процесса;
- студент пока не получает отдельное уведомление о решении своей заявки;
- нет метрик и отдельного технического admin API;
- управление структурой занятий старостой выполняется через Google Sheets и
  последующий импорт;
- webhook entry points не реализованы, оба клиента используют long polling;
- политика автоматического удаления персональных данных не реализована.

Актуальный остаточный план находится в `DEVELOPMENT_PLAN.md`.
