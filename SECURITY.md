# Политика безопасности и секретов

## Секреты

- Никогда не добавлять в Git `.env`, токены ботов, private key, credentials
  service account, локальную БД, дампы и резервные копии.
- Хранить production-секреты в secret manager или защищённых переменных
  окружения, а не рядом с исходным кодом.
- Для локальной разработки задавать права `600` файлам `.env` и credentials и
  `700` каталогу `secrets`.
- Не пересылать JSON credentials в чатах, задачах, логах и скриншотах.
- Service account должен иметь доступ только к нужной таблице. Публичный доступ
  к таблице запрещён.
- При возможной утечке немедленно отозвать токен или ключ и выпустить новый.

Добавление секрета в `.gitignore` не удаляет его из истории Git. Если секрет
когда-либо попал в commit, сначала нужно отозвать его, затем очистить историю
репозитория и уведомить всех, у кого есть копии.

## Персональные данные и логи

- Не логировать ФИО, токены, credential JSON, текст приватных сообщений и полные
  идентификаторы пользователей.
- Для диагностики использовать внутренний correlation ID и обезличенные поля.
- Задавать уникальный `OBSERVABILITY_HASH_KEY` через secret manager; не хранить
  его в Git и учитывать, что ротация меняет псевдонимы пользователей в логах.
- Логи должны иметь ограниченный срок хранения и доступ только у операторов.
- Ошибки внешних API необходимо фильтровать перед записью: ответ сервиса может
  содержать адрес таблицы, имя листа или данные ячейки.

## База данных и резервные копии

- Production-БД не должна находиться в репозитории или публичном каталоге.
- Использовать отдельного пользователя БД с минимальными правами.
- Шифровать транспорт, диски и резервные копии; регулярно проверять
  восстановление.
- Доступ старосты и технического оператора периодически пересматривать.
- Для production определить сроки хранения и реализовать очистку или
  анонимизацию согласно `PRIVACY_POLICY.md`.

## Проверка перед выпуском

1. Убедиться, что `git status` не показывает `.env`, credentials, БД и логи.
2. Выполнить сканирование истории Git на секреты.
3. Проверить права service account и приватность Google-таблицы.
4. Заполнить владельца, контакт и сроки хранения в политике конфиденциальности.
5. Проверить авторизацию всех административных команд и аудит изменений.
6. Настроить ограничение доступа, мониторинг ошибок и ротацию секретов.

## Сообщение об уязвимости

До публичного запуска заполнить приватный канал: `[security contact]`. Не
публиковать сведения об уязвимости и реальные ключи в открытом issue.
